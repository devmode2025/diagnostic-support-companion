Section 1

What is a review / red-team workflow?

A structured process where a dedicated team or automated system acts as an adversarial partner, stress-testing a product, strategy, or codebase from an outsider's perspective to find weaknesses before they become real problems.

Think of it as a formal attack on your own work before it ships. The goal isn't to be negative. It's to find and fix flaws so the final output is stronger, more secure, and more resilient.

Core principles

  • Adversarial mindset. Reviewers think like an attacker, a competitor, or a skeptical stakeholder. They look for the ways a thing will fail, not just whether it is currently correct.
  • Structured process. A defined process with specific goals: testing for security weaknesses, finding logical gaps, challenging core assumptions.
  • Cross-functional, objective perspectives. The most effective red teams include experts who were not involved in building the thing, which is what overcomes blind spots and internal bias.
  • Actionable results. Clear findings sorted into fixable (you know how to solve it) and investigate (needs human judgment).

How it works in practice

Application area Focus of the red team Key activities
Software development Code and architecture Find edge cases, security holes, race conditions, resource leaks
AI and LLM systems Model behavior and safety Test for harmful outputs, jailbreaks, data leakage
Business proposals and strategy Messaging and value proposition Evaluate from the customer's perspective, look for gaps in logic

Section 3

The master diagnostic matrix

Six classes of failure. Each has a symptom you'll hear from a customer, a first guess worth testing, a narrowing method, and a heuristic worth saying out loud in an interview.

1

State and memory mismanagement

FRONTEND
Symptom
UI sluggish after ten or more interactions; the tab eats 2 GB of RAM. Or the UI flickers and fails to update after an async operation.
First guess
"Maybe a large data set is being re-rendered." / "The data changed, but the view didn't reflect it."
Narrowing
Three heap snapshots — before, during, after. Look for detached DOM nodes or climbing component instance counts. Check whether the async operation ran outside Angular's zone.
Root cause
Forgotten unsubscribe from an observable. addEventListener with no removeEventListener. setTimeout or fetch callback with no zone.run().
Tools
DevTools → Memory → Heap snapshot · Angular DevTools · performance.memory · NgZone.isInAngularZone()
HEURISTIC

If performance degrades over time, it is almost always a leak. The heap snapshot never lies.

2

API and data flow failures

BACKEND
Symptom
Intermittent 500s, only for large payloads. Or a 200 OK while the UI shows stale data.
First guess
"Maybe the database is timing out." / "The UI must be caching something."
Narrowing
Pull the exact SQL from server logs into a query analyzer. Check Cache-Control headers and look for 304s in the Network tab.
Root cause
Missing index or an N+1 query. Aggressive CDN caching or a misconfigured service worker. An ORM result cached in memory.
Tools
EXPLAIN ANALYZE · explain() · New Relic / Datadog traces · curl -v · Redis KEYS *
HEURISTIC

Always start at the network layer. curl is your truth-teller. If curl gets the wrong data, the problem is server-side; if curl is right but the UI isn't, it's client-side caching.

3

AI and LLM failures

HALLUCINATION / RETRIEVAL
Symptom
The AI invents a fake name, date, or fact. Or it ignores the first rule in the prompt.
First guess
"The model must be hallucinating." / "The user wrote a bad prompt."
Narrowing
Log the exact prompt sent — system, user, context chunks. Count tokens. Move the critical rule to the end; if the problem disappears, it's positional bias.
Root cause
Context window too small. RAG retrieval dropped the relevant chunks. Positional bias — the model forgets the middle of a long prompt.
Tools
LangSmith / Arize · tiktoken · Pinecone / Weaviate console · Promptfoo / LangFuse
HEURISTIC

If the output is wrong but grammatically perfect, the problem is in the input, not the model. Log the full prompt payload first. Then count tokens. Then check retrieval order.

4

Configuration and environment drift

INFRASTRUCTURE
Symptom
"It works on my machine." Or the deployment succeeds but the health check fails.
First guess
"Maybe the Node version is different." / "The new version must have a bug."
Narrowing
Compare lockfiles. Compare .env variables. Read deployment logs. Roll back and see what changes.
Root cause
Missing or stale env var. Dependency version mismatch. Build artifact from an old CI run. A migration that never ran.
Tools
diff dev/prod .env · npm ls --depth=0 · docker inspect · kubectl logs · CloudWatch · Sentry
HEURISTIC

When dev and prod disagree, it is almost never the code. It is the configuration. Diff the environments first, not the commits.

5

Concurrency and race conditions

MULTI-USER / ASYNC
Symptom
Users occasionally see each other's data. A counter or inventory count is wrong after heavy traffic.
First guess
"Session management is broken." / "Maybe the update is failing silently."
Narrowing
Check session_id in the request header. Check whether the backend keeps state in a static variable. Look for lost updates via row version or timestamp.
Root cause
Static variable shared across requests. Missing database-level lock. UPDATE with no version check.
Tools
Thread dumps · pstree · SELECT … FOR UPDATE · Redis INCR · Jaeger / Zipkin
HEURISTIC

If the problem is intermittent and hits random users, it is a race condition. The fix is almost always to add a lock or make the operation atomic.

6

Silent failures and logging gaps

OBSERVABILITY
Symptom
The customer reports an error and there is nothing in the logs. Generic "something went wrong" toast.
First guess
"The customer must be mistaken." / "The backend returned a 500."
Narrowing
Ask for exact timestamp and session ID, then filter logs by session ID. Check the Network tab for the exact response payload.
Root cause
try-catch that swallowed the exception. Log level too high. Unhandled exception in an async callback. Nginx 502.
Tools
ELK stack · Sentry · OpenTelemetry · Nginx error logs · PM2 logs
HEURISTIC

If there are no logs, the error was swallowed. The fix is a global error handler that logs every exception — then reproduce it and see what was hidden.

Section 4

Red-team vocabulary

Twelve terms, each with a sentence you can actually say. Aim for two or three per interview — more than that sounds rehearsed.

Adversarial mindset

Thinking like an attacker, a skeptic, or a hostile user. Instead of "does this work?", you ask "how could this fail?"

I approach every support ticket with an adversarial mindset. I don't assume the system is working correctly — I actively hunt for failure modes.

ALL STORIES

Attack surface

Every point where an adversary — or a bug — can interact with a system: user inputs, API endpoints, config files, environment variables.

When I diagnosed the AI hallucination, I mapped the attack surface: the user input, the prompt template, the RAG retrieval, and the LLM response.

AI STORY

Threat hypothesis

An educated guess about the cause — your initial thought, before narrowing. A good one is testable and specific.

My initial threat hypothesis was that the memory leak came from unsubscribed observables. To test that, I took heap snapshots.

ALL STORIES · STEP 2

Blast radius

The scope of impact. How many users, which features, total outage or partial degradation.

When the login outage was reported, I assessed the blast radius quickly. It was hitting about 20% of users, but only on the mobile app.

POSTMORTEM STORY

Red-teaming in support

Stress-testing a system by deliberately looking for failure modes — treating every customer issue as a chance to fix a systemic weakness.

My diagnostic workflow is essentially red-teaming in production. I treat the customer's symptom as an attack vector, use tools to scan for the vulnerability, and deliver a fix that hardens the system.

META-FRAMEWORK

Fixable vs. investigate

Fixable means you know the exact solution. Investigate means you need more research first.

The source map mismatch was immediately fixable. The AI hallucination was investigate — I had to log the full prompt, count tokens, and check retrieval order first.

ALL STORIES

Postmortem

A written record of an incident: what happened, why, and what will be done so it doesn't happen again.

After we resolved the outage I led the postmortem. We documented the timeline, the root cause, and the preventative action, and I made sure it stayed blameless.

POSTMORTEM STORY

Runbook

A documented set of procedures for handling common incidents.

After diagnosing the subscription leak, I wrote a runbook section on identifying and fixing memory leaks in our Angular apps, with the exact DevTools steps and a code snippet.

ANGULAR STORY

Observability

Understanding a system's internal state from its external outputs — logs, metrics, traces.

The hardest part of diagnosing the silent failure was the lack of observability. The error was swallowed by a try-catch that logged nothing. I fixed it with a global error handler.

ESPECIALLY CLASS 6

Toil

Repetitive manual work that creates no lasting value.

Our team was spending too much time on toil — manually asking customers for their browser version and OS. I built a small script that captured it from the user-agent header instead.

PREVENTATIVE RECOMMENDATIONS

SLA — service level agreement

A formal commitment to customers about response times, resolution times, and uptime.

This was a P1, which meant a one-hour SLA for initial response. I dropped everything, assessed the blast radius, and communicated our commitment within the first 30 minutes.

URGENCY

SLO — service level objective

An internal reliability target, usually more aggressive than the SLA.

Our SLO for API response time was 200 ms at p95. When we started hitting 500 ms I knew we had a problem before customers complained, and traced it to an N+1 query.

POSTMORTEM STORY

Error budget

The unreliability a system can tolerate within its SLA. A 99.9% uptime commitment leaves 0.1% to spend.

We had burned through the quarter's error budget after two major incidents. That triggered a reliability sprint where fixing root causes outranked new features.

Section 5

The two-week sprint

Roughly eighteen hours across ten working days, ending with three polished diagnostic stories you can tell out loud.

Phase 1 · Angular sabotage lab

DAYS 1–3 · 5 HRS
Day 1MON · 1.5H

The setup

  • Fresh Angular 17 repo on GitHub
  • Create main and experiment/leaky-subscription
  • Simple component with a BehaviorSubject or interval()
  • Commit the clean code
  • Sticky note: "tomorrow, I will forget to unsubscribe"
Day 2TUE · 1.5H

Plant the bug

  • Drop the unsubscribe or the takeUntil
  • Add a nav menu so you can route away and back
  • Verify it "works" with no console errors
  • Commit to the branch
  • Do not diagnose tonight. Walk away.
Day 3WED · 1.5H

Diagnose with tools only

  • Open the app. Do not look at the source code.
  • DevTools, Performance and Memory tabs
  • Navigate to the component and away ten times
  • Three heap snapshots; watch the JS heap climb
  • Write the five-step narrative — that's Story #1

Phase 2 · Postmortem deconstruction

DAYS 4–5 · 3 HRS
Day 4THU · 1.5H

Pick the postmortem

  • Cloudflare blog or GitLab incident history
  • One write-up, 2,000–3,000 words
  • Print it or save as PDF
  • Read it once, passively
Day 5FRI · 1.5H

Rewrite it in first person

  • Rewrite the whole incident as the on-call engineer
  • "At 14:03 UTC I noticed X. My initial thought was Y. I checked Z to rule it out. The root cause was W. I explained it to the VP by saying…"
  • That's Story #2

Phase 3 · AI-powered app failure

DAYS 6–8 · 5 HRS
Day 6MON · 2H

Build the customer emulator

  • Node/Express server forwarding prompts to OpenAI or Ollama
  • Simple Angular or React client
  • Get it working 100% correctly
  • Commit as the clean baseline
Day 7TUE · 1.5H

Plant the AI bug

  • Hallucination leak, or stale RAG
  • Truncate the context window, or leave old vectors in place
  • Confirm you see wrong output as the customer
  • Do not look at the server code yet.
Day 8WED · 1.5H

Diagnose under remote rules

  • Put the source code away
  • Only server logs, request and response payloads
  • The prompt is missing the first fifteen chunks — smoking gun
  • Analogy: giving a chef only the last five ingredients from a twenty-ingredient recipe

Phase 4 · Synthesis and polish

DAYS 9–10 · 3 HRS
Day 9THU · 1.5H

Polish

  • Angular story: explanation as a one-sentence analogy
  • Postmortem rewrite: trim to one page
  • AI story: add the preventative recommendation
  • Add "in the future, I would…" to all three
Day 10FRI · 1.5H

Mock interview

  • Record yourself on a voice memo
  • Three minutes, one story, out loud
  • Play it back — does it sound natural?
  • Email yourself "My 3 diagnostic war stories"

Bonus · target product misconfiguration (3 hours, if time allows)

  • Choose Sentry or Supabase, free tier
  • Spin up a tiny app with their SDK
  • Misconfigure deliberately: source map mismatch, or RLS policy failure
  • Document the error surfaces, write Story #4

The hidden job market

A large share of roles are filled through networks and referrals rather than public postings. You're not asking for a job — you're becoming a known quantity before the job exists.

It's not about what you know, it's about who knows you.

Phase 1 · Prepare

Build a list of 20–30 tech-first companies hiring support engineers and SREs without live coding challenges. Then find the people inside them who would be your future manager or senior colleague.

  • Support Engineering Manager
  • Director of Support
  • Senior SRE
  • Principal Support Engineer
  • Technical Support Lead

Your profile has to carry the story before you say a word: ten-plus years of frontend, reframed around the diagnostic and support work you actually did.

Phase 2 · Reach out

Hi [Name], I came across your profile and was impressed by your experience in [support / SRE] at [Company]. I'm a senior frontend engineer with a strong background in [key skill] looking to transition into a support engineering role. I'd love to connect and learn more about your journey, and any advice you might have. Would you be open to a quick 15-minute virtual coffee to chat?

Questions worth asking

  • How did you get started in this field, and what has your career path looked like?
  • What does a typical day look like for you as a [support manager / SRE lead]?
  • What skills matter most for success in this role at [Company]?
  • What's something you wish you'd known when you were in a similar position?
GOLDEN QUESTION

Do you know anyone else you think I should speak with?

GOLDEN RULE

Respect their time. If you said fifteen minutes, be done in fifteen minutes — unless they're the one who extends it.

Phase 3 · Cultivate

  • Follow up within 24 hours. A personalized thank-you naming a specific insight, not a form note.
  • Don't let it go cold. Comment on their posts, send a relevant article, or check in months later with an update.
  • Offer value first. Pass on a posting that fits someone in their network. Goodwill is reciprocal.

Pitfalls

  • Don't ask for a job. The point is information and rapport, not an offer on the spot.
  • Don't send a generic message. Show you've done the research.
  • Don't sound robotic. Adapt the template until it sounds like you in a coffee shop.
Section 12

Interview scripts

Three answers worth having ready word-for-word, then loosening until they sound like you.

The title gap — when they ask about your frontend background

That's a great question. While my official title was frontend engineer, a significant portion of my work was actually support engineering in disguise. I was the person the team came to when a production issue was too complex to diagnose. I traced bugs across the whole stack, communicated findings to non-technical stakeholders, and wrote runbooks so the team could resolve issues faster. I realized I was most energized not by building new features, but by diagnosing complex problems and helping customers — so I decided to formalize that skillset and pursue support engineering directly.

The cold start — when you can't reproduce it locally

I'd ask the customer for three things:

  1. Their exact input or request payload
  2. Their session ID or request ID
  3. A HAR file — a network trace from their browser

With those I can replay their request against staging with debug logging on. That's how I found the root cause — the logs showed the specific evidence. I didn't need to remote into their machine, I just needed their data.

The red-team connection — showing you see the big picture

I approach diagnostic work the same way I'd approach a red-team security review. The goal isn't to confirm the system works, it's to actively hunt for failure modes. When a customer reports a problem, I treat their symptom as an attack surface. I start with a hypothesis, use tools to narrow it, and classify the root cause as either fixable — I have a solution — or investigate, meaning it needs deeper research. My postmortem write-ups always include a preventative recommendation, which is the same as the actionable results phase of a red-team workflow. This mindset has helped me consistently find root causes that others miss.
